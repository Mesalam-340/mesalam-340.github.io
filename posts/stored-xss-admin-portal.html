Stored XSS in Admin Portal via dangerouslySetInnerHTML in Delete-Confirmation (Events & Actions)

Omar Mesalam • Bug Bounty • Stored XSS

XSS Initial Discovery 🔍

I was testing the admin portal and found a feature called Events & Actions that allows any account member (not just admins) to create an Action, such as a webhook. This Action has a free-text field called name that gets stored server-side as-is via:

POST /api/keysets/{subscribe_key}/actions

I noticed that this name field is returned in the response exactly as submitted, with no sanitization or escaping. So I decided to test what would happen if I injected HTML into it instead of a normal string

XSS Payload Modification

I sent the following request while logged in as a regular (non-admin) account member:

POST https://admin.example.com/api/keysets/sub-c-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx/actions Content-Type: application/json Cookie: __Host-Admin-Id=...; __Host-Admin-Token=... { "name": "<img/src=x onerror=alert(document.domain)>", "category": "webhook", "configuration": { "target": "https://example.com/hook", "additionalHeaders": {}, "retryEnabled": false, "BatchConfig": { "batchingEnabled": false } }, "eventListeners": [] }

I got back a 201 Created, and the value was stored exactly as sent:

"name": "<img/src=x onerror=alert(document.domain)>"

This meant any part of the UI that displays the Action's name would render it as real HTML instead of plain text.

XSS Response Tampering & Trigger ⚡

The next question was: where exactly does this name get rendered without escaping?

I went to the Events & Actions page in the UI:

/account/<account_id>/app/<app_id>/key/<key_id>/events-and-actions

And found the row listing the Action with the name <img/src=x onerror=alert(document.domain)> displayed literally. I clicked the row's Delete button (data-tracking-id="BUTTON-delete"), which opened a delete-confirmation dialog. The problem is that this dialog renders its message using dangerouslySetInnerHTML, with no sanitization at all:

<p>Are you sure you want to delete <img src="x" onerror="alert(document.domain)">?</p>

Since src="x" doesn't resolve to a real image, the onerror handler fires immediately on render — popping an alert box showing admin.example.com

I confirmed this twice in production, against my own test tenant:

  1. Automated: injected <img/src=x onerror=window.__xssfired=1> and confirmed the handler ran (window.__xssfired === 1)
  2. Manual: injected <img/src=x onerror=alert(document.domain)> and actually clicked Delete, triggering the alert

No third-party customer data was accessed, and the test records were removed after verification

XSS Result & Impact

This is a Stored XSS on the admin portal's own origin (admin.example.com). Any low-privilege member can plant the payload, and if any other user — including an account owner or operator — later opens Delete on that same Action, the code executes inside their session, with no interaction required beyond them trying to delete or clean up a record

This opens the door to:

  • Reading full keysets, including secret keys, via GET /api/keys?app_id=<id>
  • Registering OAuth clients or abusing a consent loopback to mint org-scoped tokens
  • Modifying account and service settings
  • Defacing or persistently disrupting the admin UI

In short: full privilege escalation — a low-privilege member can reach owner-level impact just by waiting for the owner to try deleting something

  • However, unfortunately, the vulnerability was classified as a duplicate
