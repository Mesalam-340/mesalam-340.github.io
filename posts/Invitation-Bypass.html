Bypassing Group Invitation Flow via Response Manipulation

Initial Discovery 🔍

During a test on one of the websites, I found a feature that allows the group owner to add people to the group

I noticed that the application handles the email in two different ways: If the email already has an account on the platform, it gets added to the group directly. If the email doesn't have an account, the application sends an invitation instead. After cleaning up the request and keeping only the important parameters, I started testing different things on this feature.

Payload Modification

At first, I tried a few things like Host Header Injection and sending multiple emails in the same request

Then I thought: What if I can make an email that doesn't have an account look like an existing user to the application?

So I tried changing the request to:

{
  "email": "example@gmail.com",
  "user_type": "admin",
  "status": "invited"
}

The request was accepted with 200 OK.However, changing these values in the request didn't actually change anything on the backend. So I started looking at the response instead.

Response Tampering & Bypass ⚡

I intercepted the response coming back from the backend and removed the field that was telling the frontend that the email was an invited/unregistered user.

After sending the modified response back to the application, something interesting happened.

The frontend no longer treated the email as an unregistered user that needed an invitation. Instead, it treated it like an existing user on the platform.

Result & Impact:

I went back to the group management page and the email was now shown as a normal group member.

The interesting part is that this email didn't actually have an account on the platform.

Normally, the application should have sent an invitation and waited for the user to create/accept the invitation.

Instead, by manipulating the response, I was able to bypass this invitation flow and make an unregistered email appear as an existing group member.
