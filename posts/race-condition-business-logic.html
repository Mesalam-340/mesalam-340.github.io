How Race condition leading to business logic flaws affecting

  • — Group uniqueness validation
  • — Subscription enforcement limits

The First Bug 🐞

While browsing the website, I noticed a feature for creating groups and decided to create one.

After that, I decided to create another group with the same name

However, I found that the site did not allow that, so it occurred to me why not try the race condition on this endpoint?

And it has already succeeded ✅

But I wondered how this might affect other users, as I found that these groups are created with the same name but with a different ID for each group.

I discovered that I couldn’t edit this group due to name duplication, so I deleted the existing groups and created new ones with the same name but with different users having admin privileges. I found that if there are multiple groups with the same name and members, I can never edit the group, even though I own it, and I can’t reduce their privileges or control them.

Second Bug 🐞

I reasoned that since one endpoint was vulnerable to the race condition, there could be other endpoints with the same vulnerability. I tried checking multiple endpoints but found nothing, but something caught my eye

Why can’t I run a test on the endpoint that allows me to add members? Initially, I need to test adding more than five members without any procedures, but when I tried to add the sixth person, rejected.

Here I decided to conduct a test of sending invitations to more than five members using the repeater.

And it has already succeeded ✅

Of course, as we all know, nothing good lasts forever 😂

During the reporting phase, I encountered a common hurdle in Bug Bounty programs: the Scope and Exclusions policy. While the second bug (Subscription Bypass) was explicitly excluded under product feature usage limits, the first bug remained a gray area that demonstrated a significant security impact beyond mere limits

So, this means that if you use the Race Condition technique to bypass a numerical limit (such as adding more members than allowed, or unlocking paid features for free), this is completely excluded from rewards. The company considers this type of vulnerability to be known to them and not a security risk to other users’ data; it’s simply a “manipulation” of the free or paid version’s limitations.

Why is the “Group Duplication” vulnerability different?

Based on this text:

The Member Bug (Bug 2) falls directly under this category because it exceeds the “Feature usage limit” (the 5-member limit). Therefore, it’s excluded.

The Group Duplication Bug (Bug 1): If you present it as “I was able to create more than one group with the same name,” there’s a high probability it will be rejected, and I have a feeling they will anyway 😂. However, if you present it as a “Broken Access Control” because you lost control over members and their permissions, then you’re moving from the realm of “numerical limitations” to the realm of “security logic errors
